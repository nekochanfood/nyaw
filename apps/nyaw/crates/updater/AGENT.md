# crates/updater

層: 5（画面そのものではなく、ダッシュボードと設定画面が共有する更新の状態）

アプリケーションの自動更新機能を提供する。GitHub Releases を定期的に確認し、現在の実行バイナリよりも新しいビルドを検出した際にユーザーへ通知する。ダウンロードおよび更新の適用は、ユーザーが明示的に承認した場合にのみ実行される。

本クレートが持つのは、更新の状態（GPUI のグローバル `Updater`）、チャンネルに応じた推奨リリースの選択（`newest`）、および画面からの操作（確認・インストール）だけである。リリース一覧の取得、インストーラーのダウンロードと検証、インストーラーの起動は [`crates/subsystems/update`](../subsystems/update/AGENT.md) が行い、本クレートは OS の API（通信・ファイル・プロセス）を直接使わない。

## バージョン表記とビルド番号による新旧判定

本システムでは、リリースの新旧判定にバージョン文字列を用いず、直線的なコミット数に基づくビルド番号を使用する。

- **バージョン表記**: バージョン文字列は `v<CalVer>[-<チャネル名>.<番号>]`（例: `v2026.0.1`、`v2026.0.1-beta.1`）の形式をとる。チャネル名には任意の文字列が設定可能なため、バージョン文字列の辞書順比較では厳密な新旧を判定できない。
- **ビルド番号の採番**: `git rev-list --count HEAD` によって算出される HEAD までの通算コミット数をビルド番号とする。`main` ブランチはリベースマージによる直線的な履歴を維持するため、後のコミットほど確実に大きな値となる。
- **メタデータの埋め込み**:
  - ビルド時に `build.rs` が環境変数経由でビルド番号（`BUILD`）を埋め込む。
  - GitHub Actions のリリースワークフローは、リリースノートの末尾に不可視の HTML コメント形式で注釈 `<!-- nyaw-build: <番号> -->` を自動付与する。
  - アプリケーションは GitHub Releases API の単一のレスポンスからこの注釈を解析し、更新可否を即座に判定する。注釈が存在しないリリースは安全のため対象外とする。

## 配信チャンネルの運用

更新チャンネルは設定（`update_channel`）によって切り替える。

- **安定版（`stable`、既定値）**: 正式リリースのみを対象とする。GitHub 上でプレリリース（`Release::prerelease`）に指定されたものは除外される。
- **ナイトリー（`nightly`）**: 正式リリースに加え、プレリリース（alpha や beta など）も更新対象として提示する。
- **ダウングレードの抑止**: チャンネルを問わず、現在動作中のビルド番号より小さい（古い）リリースが提示されることはない。

## 更新プロセスの進行

更新は、実行中のビルドの配布形式（`Package::current`）のアセットを適用する。配布物から起動していないビルド（Linux の `cargo build` の成果物など）では、既定のリリース一覧の URL を空にし、`check_now` は一覧を参照せずに「このビルドはリリースの配布物から導入されていない」旨のエラーを設定する。テストは一覧の URL を差し替えるため、どの OS でも同じ手順を検証できる。

1. **リリースの確認 (`check_now`)**:
   - バックグラウンドスレッドで GitHub API（`GET /repos/<owner>/<repo>/releases?per_page=30`）を呼び出す。
   - ダッシュボード起動時、以降 6 時間ごと、および設定画面の「今すぐ確認」押下時に実行される（リリースビルドのみ）。
2. **更新の通知**:
   - 新しいビルドが検出された場合、ダッシュボードの操作バー上に更新ボタン（`dashboard-update`）を表示し、設定画面のアップデート詳細ページにリリースノート（Markdown）と更新ボタンを表示する。
3. **ダウンロードと検証 (`install`。処理は `update::download`)**:
   - ユーザーが「アップデートして再起動」を押下した場合のみ、インストーラーを `update::download_dir` へダウンロードする。
   - ファイルサイズと SHA-256 チェックサムを GitHub 提供のメタデータと照合し、不整合があれば処理を中断する。
4. **適用と再起動（`update::run_installer`）**:
   - 別スレッドで適用する（`Step::Applying`）。Linux のパッケージは認証とインストールの完了を待つため、画面にはデスクトップでの認証が必要になる場合があることを表示する。
   - 成功したらアプリケーション本体を終了する。再起動の方法は配布形式ごとに異なる（[`crates/subsystems/update/AGENT.md`](../subsystems/update/AGENT.md)）。

画面を起動せずに同じ手順を実行する `update_headless` は、起動オプション `--update` が使う。

## 主な公開 API

```rust
VERSION;                 // 表示用バージョン文字列
BUILD;                   // 現在のビルド番号
newest(releases, ...);   // チャンネルに応じた推奨リリースの選択
Updater;                 // GPUI グローバルリソース（進捗状態の管理）
check_now(cx);           // リリース確認の開始（別スレッド）
install(cx);             // ダウンロードと適用（ユーザーの操作時のみ）
update_headless(..);     // 画面を起動せずに確認から適用まで行う（--update）
Package; Release; Installer; start_installer; // update サブシステムの再エクスポート
```

## テスト手法

- **単体テスト (`src/tests.rs`)**: チャンネルとビルド番号による推奨リリースの選択、および確認からインストール・終了までの状態遷移を検査する。通信先は `update` サブシステムのループバックの「GitHub」（`update::fake`）を使う。リリースのパース、ダウンロードの検証、インストーラーの引数は [`crates/subsystems/update`](../subsystems/update/AGENT.md) のテストが扱う。
- **E2E シナリオテスト (`crates/testkit/tests/scenarios/update.rs`)**: 設定画面上における更新確認からダウンロード、およびインストーラー呼び出し直前までの遷移を検証する。
