# crates/subsystems/update

層: 1 Subsystems

アプリの更新に必要な OS 側の処理を担当する。GitHub Releases のリリース一覧の取得とパース、実行中のビルドと同じ配布形式のアセットのダウンロードとサイズ・SHA-256 の検証、および更新の適用と再起動を行う。どのリリースを推奨するか、いつ確認するかは上位の [`crates/updater`](../../updater/AGENT.md) が決める。

通信（`ureq`）、ファイル、プロセスを扱う処理を本クレートに置くことで、`updater`（層 5）は OS の API を直接使わない。配布形式とファイル名の規則を扱うコードは本クレートにしかないため、配布方式を追加する場合も、変更は本クレートに閉じる。以下では、各形式でダウンロードして適用するファイルをインストーラーと呼ぶ。

## 配布形式の判別

`Package` が配布形式を表し、アセット名（`nyaw-<バージョン><形式ごとの末尾>`）との対応を持つ。実行中のビルドの形式（`Package::current`）は次のように判別する。`None` のビルドは更新できない。

| 実行中のビルド | 判別の方法 |
|---|---|
| Windows | 常に Windows のインストーラー |
| AppImage | `os::running_appimage`（ランタイムが設定する環境変数） |
| tar.gz、deb、rpm、pkg.tar.zst | 実行ファイルの隣の更新情報（`update-info`） |
| その他（`cargo build` の成果物など） | `None` |

更新情報は、AppImage の更新情報と同じ書式の 1 行 `gh-releases|<所有者>|<リポジトリ>|<latest / latest-all>|<アセット名のパターン>` である（`UpdateInfo`）。配布形式はアセット名のパターンから、取得先は所有者とリポジトリから決める。4 番目の項目は外部の利用者向けの情報であり、アプリは使わない。アプリが対象にするリリースは、利用者が設定する更新チャンネルで決まる。

## リリース一覧の取得とパース

- `check(url, package)` は GitHub の API からリリース一覧を取得し、`parse_releases` でパースする。下書きと、`package` のアセット・SHA-256（アセットの `digest`）・ビルド番号のいずれかが欠けたものは除外する。
- ビルド番号はリリースノート末尾の注釈 `<!-- nyaw-build: <番号> -->`（リリースワークフローが追加する）から読む（`notes_build`）。
- 一覧の URL（`releases_url`）は、更新情報のリポジトリから作る。更新情報がないビルドでは `Cargo.toml` の `repository` を使う。
- 配布物の更新を検証するため、環境変数 `NYAW_UPDATE_URL` で一覧の URL を差し替えられる。受け付けるのは `http://127.0.0.1:<ポート>/` で始まる URL だけである。他のホストを指定できると、環境変数を設定するだけで別のサーバーのファイルが更新として適用されるためである。

## ダウンロードと検証

`download` はインストーラーを指定のディレクトリへ保存し、サイズと SHA-256 を照合する。不一致の場合はファイルを削除してエラーを返す。ファイル名がどの配布形式の規則にも合わないもの（パス区切りを含むものを含む）は取得しない。既定の保存先（`download_dir`）は、Windows では一時ディレクトリの下、Linux では `os::data_dir` の下の `update` である。Linux の一時ディレクトリは利用者間で共有されるためである。

| 対象 | 上限サイズ | タイムアウト時間 |
|---|---|---|
| リリース一覧取得 | 4 MiB | 30 秒 |
| インストーラーダウンロード | 512 MiB | 30 分 |

## 適用と再起動

`run_installer` / `start_installer` はインストーラーを適用して再起動を手配する。呼び出し側は、成功後にアプリを終了する。

### Windows

インストーラーをサイレント引数（`/VERYSILENT /SUPPRESSMSGBOXES /NORESTART /SP- /WAITPID=<pid> /RELAUNCH=1 /ARGS=<再起動時の引数>`）で起動し、完了を待たずに戻る。インストーラーは nyaw のプロセスの終了を待ってからファイルを置き換え、再起動する。再起動時の引数は空白で結合されるため、空白・引用符を含むものは渡さない（`installer_args`）。

### Linux での適用

適用の完了まで戻らないため、別スレッドで呼び出す（`src/linux.rs`）。

- **AppImage**: 同じディレクトリに複製してから名前を変え、実行中の AppImage ファイルを置き換える。パスが変わらないため、SteamVR の自動起動の登録はそのまま使える。
- **tar.gz**: 展開先を実行ファイルのディレクトリの下に作り、アーカイブに含まれるファイルを 1 つずつ置き換える。他のファイルは変更しない。
- **deb、rpm、pkg.tar.zst**: `pkexec` で `src/linux/install-package.sh` を root で実行する。認証を待つ間に利用者の権限でダウンロード済みのファイルを差し替えられると、別の内容が root でインストールされる。そのためスクリプトは、root だけが書き込める場所に複製してから SHA-256 を照合する。更新の新旧はビルド番号で判定するため、パッケージのバージョンの順序では古くなる版も適用する。また、apt と dnf は同じバージョンが導入済みだと何もせずに正常終了するため、同じバージョンでもファイルを置き換える指定をする。指定しないと、置き換わっていないのに更新できたと判断し、同じ更新を案内し続ける。

適用後は、呼び出し元の終了を待つシェルを別のプロセスグループで起動し、終了を確認してから同じ引数で起動し直す。パッケージを置き換えた後の `current_exe` は削除済みのファイルを指すため、起動するパスは適用の前に取得する。

## 主な公開 API

```rust
Package; UpdateInfo;                    // 配布形式と、配布物に同梱する更新情報
Release; Installer;                     // リリースと付属インストーラーの情報
check(url, package);                    // リリース一覧の取得（別スレッドで呼ぶ）
parse_releases(json, package);          // リリース一覧のパース
releases_url();                         // 一覧を返す GitHub API の URL
download(release, dir, ..);             // ダウンロードとサイズ・SHA-256 の検証
download_dir();                         // 既定のダウンロード先
run_installer(path, installer);         // 適用と、現在と同じ引数での再起動の手配
start_installer(path, installer, args); // 適用と再起動の手配（再起動の引数を指定する）
fake;                                   // ループバックの「GitHub」（test-support フィーチャー）
```

## テスト手法

- **単体テスト (`cargo test -p update`)**: ビルド番号の読み取り、配布形式とアセット名の対応、更新情報の解析、リリースの除外条件、インストーラーの引数、およびループバックの「GitHub」（`fake`）を用いたダウンロードとサイズ・SHA-256 の検証を検査する。Linux では、AppImage と tar.gz の置き換え、および呼び出し元の終了後の起動も検査する。
- **インストールのスクリプト**: root とパッケージマネージャーが必要なため、単体テストには含めない。CI の `installer/smoke.sh` が各ディストリビューションで実行し、SHA-256 が一致しないパッケージを導入しないことと、再導入でファイルが置き換わることも確認する。
